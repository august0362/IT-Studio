# WC-03 — Free-floating web-chat windows (drag, resize, maximize, minimize, overlap)

Milestone: v1 owner acceptance feedback (2026-10-16) · **After WC-02 lands** · Role: Implementer · Size M–L · **Deps pre-installed (no new crates/packages)** · **Broad scope: `apps/desktop/src/features/webchat/**`, `apps/desktop/src/**` web-chat host/state files, `apps/desktop/src-tauri/src/webchat.rs` (+ the command registration/capabilities it needs), web-chat layout settings in `src/types/schemas.ts` (additive) and `apps/sidecar/src/**` validation/normalisation for them — do not stop for edits needed to meet a requirement; list them in Result** · D34 still applies.

## Owner request

"In the web-chat area I want to drag the panes freely, maximize and minimize them, smoothly, and let them overlap other panes."

## Background

Each pane is a **native child webview** (Tauri, `webchat.rs`) placed over the React page; React only computes bounds and calls `webchat_sync`. Native webviews always paint above the main webview, so HTML chrome drawn under them is hidden, and moving them every pointer event is janky.

## Requirements

1. **Layout mode switch** in the Web chat toolbar: **Tiled** (today's 1–4 split panes, unchanged) and **Free** (floating windows). The mode is persisted.
2. **Free mode window frame (React):**
   - Title bar: site icon/initial, name, buttons *Minimize*, *Maximize/Restore*, *Open in browser*, *Close*. All are labelled buttons.
   - Drag by the title bar; resize from the 4 edges and 4 corners (min 360×280, clamped inside the web-chat area).
   - Double-click the title bar maximizes or restores. Optional edge snap (half/full) when released near an edge.
3. **Z-order and overlap:**
   - Clicking a window or its title bar brings it to the front. Windows may overlap.
   - The native webview of each window is placed inside its frame below the title bar.
   - Native z-order must follow the React z-order. Implement a `webchat_raise(paneId)` command in `webchat.rs` that brings that child webview to the top. Research the Tauri 2 / WebView2 API in the pinned versions (e.g. re-adding or reordering the child webview, or `SetWindowPos` on the controller's parent HWND).
   - Window titles must never be hidden under another window's webview: the frontmost window's title bar is drawn in a thin native-free strip, or other webviews are clipped/hidden where they intersect. Choose the approach that works and document it.
   - If true native z-order is impossible, write `## Blocked` with evidence instead of faking it.
4. **Smoothness:**
   - While dragging or resizing, hide the moving window's native webview and show a lightweight placeholder (site name, icon, subtle glass/blur style) that follows the pointer at 60 fps via `requestAnimationFrame`.
   - On release, sync the bounds once and show the webview again. Other windows stay live.
   - Maximize/restore/minimize animate the frame (150–250 ms), then sync.
   - Respect `prefers-reduced-motion`.
5. **Minimize:** minimized windows go to a dock bar at the bottom of the web-chat area (chips with icon + name); clicking a chip restores the window and brings it to the front. Minimized panes hide their native webview but keep their session.
6. **Persistence:** per window, position, size, maximized/minimized state and z-order are saved in the existing web-chat layout settings (additive fields, validated and normalised) and restored on reopen. Tiled-mode layout is untouched.
7. **Limits:** up to 6 windows in Free mode (4 in Tiled as today). Opening a site that is already open focuses its window.
8. **Keyboard/a11y:** focusable title bar; `Alt+Arrow` moves a focused window by 24 px and `Alt+Shift+Arrow` resizes it; Esc during a drag cancels it.

## Answer to Blocked (Architect, 2026-10-22) — owner wants real overlap

Owner decision: windows must overlap normally. Use Win32 directly (Windows only). The Architect added the dependency to `apps/desktop/src-tauri/Cargo.toml`: `[target.'cfg(windows)'.dependencies] windows = { version = "0.62.2", features = ["Win32_Foundation", "Win32_UI_WindowsAndMessaging"] }` (already in Cargo.lock as a transitive crate; `cargo check` passes). Do not add other crates.

Implement `webchat_raise(pane_id)` in `webchat.rs` exactly like this:
1. Get the main window HWND via Tauri (`window.hwnd()` on the main `WebviewWindow`, Windows-only API).
2. Get the target child webview's current bounds (you already track them per pane for `webchat_sync`), in physical pixels relative to the main window client area.
3. `EnumChildWindows(main_hwnd, …)` collecting **direct** children whose class name starts with `Chrome_WidgetWin` (WebView2 host windows). For each, `GetWindowRect` → convert to client coordinates (`ScreenToClient` / `MapWindowPoints`) and pick the one whose rect equals the pane bounds (±2 px tolerance). If none/ambiguous, return an error `"raise target not found"` (do not guess).
4. `SetWindowPos(hwnd, HWND_TOP, 0, 0, 0, 0, SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE)`.
5. Put the Win32 code in a small `#[cfg(windows)] mod zorder` with a pure helper `pick_by_bounds(candidates: &[(isize, Rect)], target: Rect, tol: i32) -> Option<isize>` that is unit-tested in `webchat_tests.rs` (exact match, tolerance, none, two matches → None). Non-Windows builds: `webchat_raise` returns Ok(()) no-op.
6. Register the command and its capability permission like the other `webchat_*` commands; React calls it whenever a window is brought to front (click/title-bar/dock restore), after `webchat_sync`.
7. Title bars must stay visible: when a window is raised, the windows it overlaps keep their webviews but their frames sit below; the raised window's title bar is drawn in the React layer **above** its own webview bounds (the native webview starts below the title bar), so it is never covered by its own webview; other windows' webviews covering it is correct overlap behaviour.

Then make JS checks pass (QA runs typecheck/lint/tests outside the sandbox if the sandbox blocks esbuild), replace `## Blocked` with `## Result`, and state the z-order technique used.
