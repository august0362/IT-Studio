# M10-04 — `start_pipeline` tool with user confirmation

Milestone: M10 · Depends on: M10-03 · Role: Implementer · Size M · **Deps pre-installed**
Requirements: FR-AG-09 · DD-V2-02 · SRS v2 §7.1

## Goal
An agent can propose a code-pipeline run, but nothing is spent until the owner clicks *Start* (optionally after editing the prompt).

## Read first
SRS v2 §1.5 DD-V2-02, §3.1, §6.3 (`agents.confirmPipeline`, `agents.dismissPipeline`), §7.1, `services/pipeline-orchestrator.ts`, `services/agent-runner.ts`, `services/agent-tools/*`.

## Scope
- `apps/sidecar/src/services/agent-tools/start-pipeline-tool.ts` (+ test), `services/agent-runner.ts` (awaiting_approval handling), registry wiring
- `src/types/schemas.ts`: RPC `agents.confirmPipeline`, `agents.dismissPipeline`; validators; `container.ts`
- integration `apps/sidecar/test/integration/agent-pipeline.test.ts`

## Requirements
1. Tool args `StartPipelineArgs` (prompt 1–8 000 chars). Execution does **not** call the orchestrator; it stores `pendingPipelinePrompt` on the run and returns `{status:'awaiting_confirmation'}` to the model, which writes its final message; the run ends in `awaiting_approval`.
2. At most one pending pipeline proposal per run (second call → error result).
3. `agents.confirmPipeline(runId, prompt)`: run must be `awaiting_approval`; prompt validated; calls `pipeline.start` for the run's project (respects one-run-per-project queue); records `pipelineRunId`; run → `completed`; emits `agent.run`.
4. `agents.dismissPipeline(runId)` → `completed` without a pipeline.
5. Only triggers `ui` and `vscode` (policy already enforces); external → never registered as allowed.

## Tests
Unit: tool parse/limits, second proposal rejected, confirm/dismiss transitions, confirm on wrong state → `CONFLICT`. Integration `TC-M10-012`: scripted tool call → run `awaiting_approval`, no pipeline row; confirm → pipeline run exists with the edited prompt.
