# M13-05 — Email commands: acceptance policy and confirmed run

Milestone: M13 · Depends on: M13-02 · Role: Implementer · Size M · **Deps pre-installed**
Requirements: FR-GM-07, FR-GM-08 · D23 · SRS v2 §7.3

## Scope
- `apps/sidecar/src/domain/email-command-policy.ts` (+ test), `domain/authentication-results.ts` (+ test: parse `Authentication-Results` headers), Gmail sync hook storing `meta.commandCheck: CommandCheck`, `services/gmail/gmail-command-service.ts` (+ test), `src/types/schemas.ts` RPC `gmail.runCommand` + validator, `container.ts`
- Desktop: Inbox message detail shows command chips (from `meta.commandCheck`) and a *Run command* confirmation dialog (agent select, "allow pipeline" checkbox, request preview) — `features/inbox/CommandDialog.tsx` (+ test)

## Requirements
1. Policy exactly SRS §7.3. Sender match: address compare case-insensitive on the `From` address (not display name). Prefix: subject trimmed starts with `[ITS]` (case-sensitive brackets, case-insensitive letters). DKIM: some `Authentication-Results` header from Google (`mx.google.com`) contains `dkim=pass` with `header.d` (or `header.i`) equal to or a parent of the sender domain; anything else = fail.
2. Command messages are triaged as `command` (M12-04 coercion uses `isCommand`).
3. `gmail.runCommand(messageId, allowPipeline, agentId?)`: message must have `isCommand`; runs the agent with trigger `channel_action` **but** with the owner-command tool set = agent tools ∩ {search_knowledge, recall_memory, draft_reply, start_pipeline if allowPipeline}; the run's final answer is drafted as a reply to the Outbox (always, even without a `draft_reply` call).
4. Nothing runs at sync time (D21); commands wait for the owner's *Run*.

## Tests
Decision table R1–R5 + header parsing corpus (multiple AR headers, spoofed AR from non-Google host ignored, subdomain alignment, `dkim=fail`, missing header); service: non-command rejected, allowPipeline false/true tool sets, reply drafted. Component test for the dialog.
