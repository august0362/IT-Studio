# M16-05 — Alert engine (pure) and alert service

Milestone: M16 · Depends on: M16-04 · Role: Implementer · Size M · **Deps pre-installed**
Requirements: FR-AL-01, FR-AL-02 · SRS v3 §7.2 · ARCH §19.3

## Scope
`apps/sidecar/src/domain/alert-engine.ts` (+ test), `services/metrics/alert-service.ts` (+ test), notification `server.alert` in `schemas.ts` + validator, `container.ts`.

## Contracts
```ts
type AlertState = { phase: 'inactive' } | { phase: 'pending'; since: IsoDateTime } | { phase: 'firing'; since: IsoDateTime };
export function evaluate(rule: AlertRule, state: AlertState, observation: { at: IsoDateTime; value: number | null; online: boolean },
  ): { state: AlertState; emit: 'fired' | 'resolved' | null };
```

## Requirements
1. Conditions: `offline` → !online; `cpu_percent`/`mem_percent` > threshold; `disk_percent` → any disk > threshold (value = max); `battery_percent` → battery discharging and percent < threshold; `container_exited` handled by event (M17-02 calls `raise(serverId, 'container_exited', message)` → fires and auto-resolves on the next container start event).
2. `forSeconds` debounce measured with observation timestamps (not wall clock); `forSeconds = 0` fires on the first matching sample.
3. Disabled rule → state reset to inactive without emitting.
4. Service keeps state per (server, metric) in memory; emits `server.alert` with a human message (en; UI translates by metric + value); rules from settings (live reload).

## Tests
Table-driven: each metric × (below, at, above threshold) × forSeconds (0, 60) × sequences (flap before 60 s, sustained, resolve); offline after 30 s; disabled mid-pending; battery charging ignored.
