# M10-05 — Routing rules: repository, matcher, `routing.*` RPC

Milestone: M10 · Depends on: M10-01 · Role: Implementer · Size M · **Deps pre-installed**
Requirements: FR-AG-13 · ARCH §15.3

## Goal
Ordered rules decide which agent processes an inbound channel message (used from M12 on); the owner can test a rule set before using it.

## Read first
SRS v2 §3.1, §5 (`routing_rules`), §6.3 (`routing.list|save|test`), `schemas.ts` §14 `RoutingRule`.

## Scope
- `apps/sidecar/src/domain/routing-match.ts` (+ test), `ports/routing-repository.ts`, `infra/sqlite/routing-repository.ts` (+ test), `infra/sqlite/schema.ts` (migration by QA), `services/routing-service.ts` (+ test), validators, `container.ts`, `src/types/schemas.ts` (the three RPC entries)

## Requirements
1. Pure `match(rules, msg) → RoutingRule | null`: rules sorted by `order`, enabled only, all present conditions must match (case-insensitive substring, Unicode-normalised NFC, trimmed), empty `match` = catch-all.
2. `routing.save` replaces the full list atomically (transaction), renumbers `order` 1..n, max 100 rules, agent must exist and include the rule's channel in `agent.channels` (else `VALIDATION`).
3. `routing.test` returns the matching rule and agent (or nulls) without side effects.
4. `resolveAgent(msg, account)` service method: rule → account `defaultAgentId` → `null` (caller asks user).

## Tests
Matcher table: no rules, catch-all, multiple conditions, disabled skipped, order wins, Vietnamese diacritics case-insensitive; save validation (101 rules, unknown agent, channel mismatch); integration `TC-M10-020` save → test → list round trip.
